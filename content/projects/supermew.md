# SuperMew

**面向知识与数据分析的智能体平台**

[GitHub ↗](https://github.com/icey1287/SuperMew)

SuperMew 以知识库为中心，把检索、推理、工具执行和效果评估放进同一套 Agent 运行体系。它关注的不只是“生成一次回答”，还包括一次任务如何持续执行、如何暂停等待确认、如何恢复，以及回答中的证据是否经得起检查。

技术栈：`Python` · `FastAPI` · `LangGraph` · `PostgreSQL` · `Redis` · `Milvus` · `Vue 3` · `TypeScript`

## 从聊天接口到 Agent 运行时

一次任务被拆分为可以持久化、重放和审计的领域对象：

| 对象 | 职责 |
| --- | --- |
| Thread / Message | 保存会话边界、用户输入和事实历史 |
| Run | 表示一次可恢复的 Agent 执行 |
| Event Journal | 记录执行事件，支持重连与补放 |
| Checkpoint | 保存人工确认前的执行状态 |
| Document Version | 固定本次检索所使用的知识版本 |

执行事件先写入 PostgreSQL，再经 SSE 展示给前端；前端按事件序号去重，并通过 `Last-Event-ID` 和事件补放恢复观察。Redis 负责低延迟通知，持久化的执行记录负责保存结果。

## 会规划、会判断证据的 RAG

简单的单事实问题优先走低延迟检索路径；复杂问题由 Fast 模型规划，拆成 2–4 个子问题，通过 LangGraph 并行检索和判断证据，最后去重、合成回答。

```text
问题与上下文
    ↓
复杂度判断 / 子问题规划
    ↓
Dense + BM25 → RRF → Auto-merging → Rerank
    ↓
证据判断：相关性 / 可回答性 / 歧义
    ↓
回答 · 重写检索 · 人工澄清
```

证据不足时，在 Step-back 与 HyDE 中选择一种重写方式，最多再检索、复评一次。遇到需要用户补充信息的情况，通过 HITL 暂停；确认后继续同一个 Run，而不是丢弃前面的执行过程重新开始。

## 细粒度召回，大粒度理解

文档的叶子分块进入 Milvus，父级分块与版本信息保存在 PostgreSQL。Dense 与 Milvus 原生 BM25 双路召回后，由 RRF 融合排序，再在完整候选池上进行父块聚合，最后按配置进入 Rerank。

这种设计把“找到精确片段”和“给模型足够完整的上下文”分开处理：召回时保持粒度，生成时尽量保留完整证据。各阶段的候选、判断与降级信息保存在 `rag_trace` 中，便于复盘一次回答是如何形成的。

## 文档更新与执行恢复

知识库上传由持久化 Index Job 处理。新版本先在独立的候选空间中构建并核验，完成后通过 PostgreSQL CAS 切换当前版本，避免索引构建过程影响正在使用的知识版本。

HITL 暂停和恢复保留 Run、Thread 与 assistant Message 的身份。停止任务会请求后端取消执行；连接断开后，仍可根据事件记录重新接续观察。

## Skill、Tool 与模型控制面

版本化的 Skill / Tool Registry 管理知识库、联网研究、只读 SQL、天气、代码沙箱和受限 HTTPS JSON 工具。模型按当前任务权限获得工具定义，运行时约束工具调用次数、递归、截止时间、上下文预算和重复调用。

模型中心分别配置 Answer、Fast、Grader、Evaluator 角色，并在任务创建时冻结 Model Snapshot。执行中的任务因此不会被后续的模型配置调整悄悄改变。

## 把评估放进迭代过程

RAG 评估包含 Dataset、Evaluation Job、Case 与独立 Worker，以及前端评估工作台。评分涵盖正确性、证据支撑、相关性、完整性、无依据陈述和冲突披露，并能与基线和质量门槛比较。

从请求轨迹到数据集回归，检索和生成的调整都可以放到同一套记录中观察。这个项目把 Agent 的运行、知识版本、工具管理与效果评估连接成一个完整系统。
