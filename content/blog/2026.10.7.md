# 当代码越来越容易生成，我们还能做什么

## 一个我理解的 Demo

2026 年 3 月，我发布过一期讲 Agentic RAG 的视频。

当时 RAG 这个概念比较火，Coding Agent 也刚开始大量涌现，所以我就用 GitHub Copilot 里面内置的 Codex 5.3，一点一点把 [SuperMew](https://github.com/icey1287/SuperMew) 这个项目敲了出来。

虽然这个项目绝大部分代码都是 AI 写的，但是那个时候，每一个模块、甚至每一行比较重要的代码，我基本上自己都是看过的。它最开始其实就是一个比较小的 Demo。

我当时也没有想着要把它做成什么特别大的东西，只是觉得 RAG 似乎就是入门 Agent 的一个很轻松的方向，我花了一些时间去用 LangChain 手搓了一些小东西，想着可以把一些最近学到的东西放进去，也可能给大家提供一些思路，比如后面还能加什么功能。

在当时就是这么一个 Demo，帮我找到了一份 Agent 开发相关的实习。

## 模型越来越强，我交出了更多权限

实习之后，我的大部分精力都放到了公司的业务上，这个开源项目就基本没怎么维护了。然后接下来发生了一件事情。模型开始变得越来越强，并且强得越来越快。GPT-5.5、Opus 4.8。

**这些模型已经强得有点变态了。**

与此同时，Agent 也越来越火。OpenClaw 之类的项目开始讨论 Harness，大家开始讲 Runtime、Skill、Sandbox、多 Agent、Computer Use……既然模型已经这么强了，那我为什么不把原来的 RAG 项目改造成一个更完整的 Agent 项目？

让它不只是检索知识，而是真的能够调用工具、执行任务、做数据分析，甚至以后变成一个完整的个人 Agent。当然，我在一开始设计那个 RAG 项目的时候也是这样设计的。我把 RAG 作为一个工具来给我的大模型调用，里面还内置了一些像天气查询之类的小工具，都是我自己写的。

## 把 Demo 变成 Product 的激进尝试

然后到了 GPT-5.6 的时候，我做了一个现在回头来看非常不好的决定。或者说是做了一次非常激进的尝试。因为当时我觉得模型能力已经强得可怕了。所以我干脆把大量权限都交给了 GPT 和 Codex，让它们自己去重构这个项目。

我让它去研究当时的一些开源 Agent 项目，看看别人是怎么做 Harness、Runtime、Tool System、Sandbox 的，然后吸取里面好的设计，再回来改造我的项目。我的想法其实特别简单：

**把一个 Demo 变成一个真正的 Product。**

听起来挺合理的。但这里面有一个非常大的问题。我的项目从一开始就只是一个练手项目。它没有特别严格的架构设计，也没有特别清晰的模块边界，更没有什么非常完整的工程规范。因为最开始做它的时候，AI 还没有现在这么强，我也没有想过它以后会膨胀成这么大的一个东西。

它本来就是我边学边写出来的。结果后来，我直接让 AI 在这样一个地基上放飞自我了。Ultra，Goal，全开。然后它开始疯狂改。到底改了多少 Token，我已经完全记不清了。几十亿，甚至上百亿可能都有。

最后给我生成了海量的 AI slop。

## AI slop：局部合理，整体失控

这里可能有人会问：

AI slop 到底是什么意思？最简单地说，就是：

**代码很多，看起来也很完整，甚至每个模块单独看都好像挺专业，但是整个系统没有一个人真正理解它。**

一个很简单的逻辑，会出现三四套实现。为了防一个理论上可能发生的问题，它能给你再套五层 abstraction。本来一个函数能解决的问题，最后多出来 Factory、Manager、Coordinator、Adapter、Runtime、Executor……

然后这些东西之间再互相调用。更恐怖的是，它不是完全错。如果它完全写错了，反而很好解决。最大的问题是：

**它每一个局部看起来都挺合理。**

所以你很难在 Code Review 的时候直接说：

> “这行代码有 Bug。”

但当整个系统膨胀到一定程度之后，你会发现：

- 一次很小的修改，会牵连很多模块；
- 同一个状态，在几个地方分别维护；
- 一个逻辑出现几套不同实现；
- 为了兼容过去某个已经不存在的设计，又保留了一堆 fallback；
- 然后为了修这些 fallback，又继续生成新的 fallback。

整个项目最后就变成了一种非常奇怪的状态：

**AI 很懂每一个局部，但没有任何人拥有整个系统。**

包括我自己。这才是最可怕的地方。

## 我已经看不懂自己的项目了

最开始我还没有意识到这个问题有多严重。我本来的计划是：

让 AI 把这次大重构做完，我再去看看它更新了什么，然后总结一些比较有意思的设计，再发一期新视频。结果它真的“做完”以后，我发现完全不是这么回事。我已经看不懂自己的项目了。更准确一点说：

不是代码本身看不懂。而是我已经不知道：

- 为什么这里要这样设计？
- 这个模块到底负责什么？
- 这个 abstraction 是真的需要，还是 AI 当时觉得“这样更工程化”？
- 这个 fallback 到底解决过什么真实问题？
- 这个状态为什么在三个地方都有？

整个项目已经失控了。

## 花一两个月，重新拿回控制

所以后来，我在工作之外又花了很长时间，一点一点把这个项目重新梳理回来。

- 删掉重复实现。
- 重新确定模块边界。
- 清理一些没有必要的抽象。
- 把状态重新统一起来。
- 重新补测试。
- 重新看调用链。

有些地方最后甚至不是“重构”，而是直接删掉重新写。这个过程前前后后花了我一两个月。但也是在这个过程中，我第一次特别明显地意识到：

**Agent 时代下的软件工程，可能和以前已经不太一样了。**

以前我们担心的是：

代码写不出来。现在很多时候，代码根本不是问题。AI 一晚上可以帮你生成以前一个人写几个月的代码。真正的问题反而变成了：

**你能不能控制这些代码。**

## 软件工程习惯，也是在管理 AI

我后来复盘了一下，之前到底错在哪里。第一个问题，就是我太相信 AI 了。有些东西其实我自己都没有想清楚。但是因为模型表现得特别自信，我就会产生一种错觉：

它好像真的理解我要什么。然后我就让它继续做。实际上很多时候，它只是非常擅长在你给出的局部信息下面，生成一个“看起来合理”的下一步。但：

**看起来合理，不等于整个系统合理。**

第二个问题，是我自己也没有遵循很多最基本的软件工程 Best Practice。比如一开始没有把 architecture 设计清楚。没有明确模块之间到底应该怎么依赖。没有把一些重要的设计约束写进 Agent.md、spec、architecture document 里面。

没有坚持小 Commit。一个任务改几十个文件，出了问题之后根本不知道是哪一步引入的。也没有给 AI 足够明确的 Verify。很多时候我的 Verify 就是：

> “你检查一下有没有问题。”

那这个其实跟没有 Verify 差不多。现在我会更倾向于告诉它：

- 跑哪些测试；
- 哪些接口行为不能变化；
- 哪些 benchmark 不能下降；
- 哪些文件不应该被修改；
- 这个改动最多允许影响哪些模块。

以前写代码的时候，这些东西可能属于“工程习惯”。但现在我觉得，它们已经开始变成一种：

**怎么管理 AI 的方法。**

## 项目的价值，正在离开技术清单

但是更有意思的事情发生在后面。当我真的花了一两个月，把这个项目重新拿回自己手里以后，我突然又开始觉得：

它好像没有那么重要了。因为现在再去做一个通用 Agent 平台，其实没有什么特别大的意义。年初的时候可能还不一样。那个时候你自己从零写一个 Agent，写一个 RAG，做一点 Tool Calling，甚至搞个简单的 Multi-Agent，确实都很新鲜。

你把它放在简历上，也很容易成为面试官感兴趣的东西。但现在呢？人人都会写。更准确一点说：

**人人都可以让 AI 帮自己写出来。**

那你再做一个：

聊天框 + Tool Calling + RAG + Web Search + Sandbox + MCP……到底有什么意义？如果只是把这些东西重新拼一遍，其实技术含量正在快速下降。除非你真的有一些非常独特的想法。

或者你找到了一个非常明确的场景。比如你真的做一个非常轻量的个人 Agent。它不是为了证明“我会写 Agent”，而是真的每天跟着你一起工作。你把重复性的事情交给它。让它处理邮件、整理信息、跟踪一些任务。

甚至让它随着你的使用不断了解你的习惯。这种东西我反而觉得可能更有意思。至于让它帮你去上课……这个就比较夸张了。虽然现在确实也有不少大学生和研究生已经在让 AI 帮自己上课、做作业了。不过，这个不是重点。

重点是：

**项目的价值正在从“我用了什么技术”，变成“它到底解决了什么问题”。**

## 后端、Agent、算法：我到底该选什么

其实这件事情和最近找工作的感受也特别像。尤其是 2027 届秋招，大家应该都能明显感觉到，整个市场和前几年已经不太一样了。我身边也有不少人，两三段大厂实习，最后秋招结果依然非常一般。所以现在很多人都会开始焦虑：

那我到底应该学什么？后端？Agent？算法？但问题是，这三个方向现在看起来好像都有问题。做传统开发，大家会担心以后 Coding Agent 越来越强，很多初级开发工作会不会被替代。做 Agent，现在又会发现很多 Agent 本身正在被通用模型和通用 Coding Agent 快速商品化。

很多公司一开始可能也想自己做一个通用 Agent，后来做着做着发现：

为什么我要重新做一个比 Codex、Claude Code 还差的东西？所以现在很多 Agent 的落地方向，反而越来越偏 To B。比如企业内部提效。或者帮传统产业做数字化、智能化转型。这些需求肯定不会突然消失。

只是“单独做一个通用 Agent”这件事情本身，可能越来越难形成长期壁垒。而做算法呢？门槛又越来越高。尤其是基础模型这件事情，越来越像少数顶尖团队之间的竞争。对于绝大部分普通人来说，想真正参与最核心的模型研发，本身就不是一件特别容易的事情。

所以很多人现在会有一种感觉：

后端不敢选。Agent 不敢选。算法也不敢选。好像选什么都怕自己刚学完，这个方向就没了。网上有一句我特别喜欢的笑话：

**“学得慢是一件好事，因为学得慢，可能过一段时间就不用学了。”**

听起来很好笑。但其实背后反映的是很多人现在真实的焦虑。技术变化的速度，已经快到大家连方向都不敢选了。

## 先保持看见变化的能力

所以我最近也一直在想：

**那我们到底还能做什么？**

我现在其实也没有一个特别确定的答案。但我至少知道自己准备做什么。第一件事情，还是保持对新技术的关注。我依然会关注新的大模型、新的 Coding Agent、新的产品、新的想法。不是说每一个出来我都要马上学。

而是至少我要知道：

- 这个行业现在正在往哪里走。
- 哪些事情正在变得便宜。
- 哪些事情正在变得重要。
- 哪些能力正在被模型吃掉。
- 又有哪些新的机会刚刚出现。

因为如果未来真的出现下一波新的浪潮，我至少希望自己能够看见它。

## 回到最开始：我喜欢做东西

第二件事情，是重新回到我最开始喜欢计算机的原因。其实我本科之前为什么会选择计算机？非常简单。小时候喜欢打游戏。后来觉得：

如果我自己也能做一些东西出来，好像挺酷的。我本科刚开始的时候，大模型甚至还没有真正出现。我第一个比较完整的项目，是自己手搓了一个酒水管理系统。大概五千行代码。现在回头看肯定写得非常烂。架构可能也不存在。

但那个东西真的是我自己一行一行敲出来的。而且最后真的能跑。那种感觉我到现在印象都很深。你会觉得：

**这个世界上原来没有这个东西，但是我把它做出来了。**

我后来发现，我真正喜欢的可能一直都是这件事情。做东西。把一个想法变成真的。以前实现一个想法，可能要花一个月。现在有 AI，可能一天就能做出来。那从这个角度来看，AI 对我来说反而不是坏事。它把“创造东西”的成本降到了一个以前完全不敢想象的程度。

## AI 放大了自学的能力

而且 AI 还有另外一个我特别喜欢的地方。就是：

**我们这一代人的自学能力，被极大地放大了。**

以前你不懂一个领域，要找书、找课程、找老师、翻 Stack Overflow。现在很多时候，我可以直接和一个模型聊两个小时。让它从最基础的地方开始讲。让它给我举例子。让我自己做题。做错了它再纠正我。

然后我可以在一天时间里接触以前可能需要一周才能理解的东西。所以最近我反而开始觉得：

或许“学什么能找到工作”当然很重要。但是在这样一个时代里，单纯享受学习本身，也是一件挺不错的事情。因为获取知识从来没有像今天这么容易过。

## 比起为了 Research 而 Research，我更想做有人用的东西

我回到学校以后，其实没有特别想去做 Research。或者更准确一点说，我没有特别想为了“做 Research”这件事情本身去做 Research。首先，我不一定做得出来特别好的东西。其次，就算最后做出了一篇论文，我也会问自己一个问题：

然后呢？这个东西有人会用吗？我自己会用吗？它真的解决了一个现实问题吗？还是它只是在某个非常特定的数据集、非常特定的假设下面，比 Baseline 高了零点几个点？这不是说 Research 没有意义。

真正好的 Research 当然非常有意义。只是对我自己来说，我可能还是更喜欢另外一件事情：

**做一个真的有人会用的东西。**

## Agent 时代的软件工程

所以最近，我又把一部分精力重新放回到了传统后端开发上。或者我现在更喜欢叫它：

**Agent 时代的软件工程。**

因为实习这几个月，我越来越明显地感觉到：

架构、系统设计、数据库、并发、缓存、可靠性，这些东西并没有因为 AI 出现就突然消失。甚至在 AI 能够生成越来越多代码之后，这些东西反而可能变得更重要。因为以前一个人一天写几百行代码。现在一个 Agent 一天可以给你改几万行。

- 那谁来判断这些代码到底该不该存在？
- 谁来决定模块边界？
- 谁来定义状态应该由谁拥有？
- 谁来判断这个 abstraction 到底有没有必要？
- 谁来设计测试？
- 谁来决定什么叫“做完了”？

谁来在 AI 生成一万行代码之后说：

**这九千行都删掉。**

我现在越来越觉得：

代码正在变得便宜。但是判断没有。实现正在变得便宜。但是设计没有。生成正在变得便宜。但是验证没有。甚至当 AI 越来越强以后，

**知道什么东西根本不应该写，可能会比知道怎么把它写出来更重要。**

## 未来难以预测，但我仍然愿意创造

当然，也有可能一年之后，连这些东西都被 AI 做得非常好了。我现在说的这些，到时候全部过时。这完全有可能。所以我现在也不太想再去预测：

未来十年什么岗位最有前途。因为可能连未来两年都很难预测。我现在更愿意相信的是：

无论模型怎么变化，有几件事情应该不会那么快消失。

- 对新东西保持好奇。
- 能够快速学习。
- 能够判断一个问题是不是真的值得解决。
- 能够把一个模糊的需求变成一个真正可运行的系统。
- 能够知道什么时候应该让 AI 写代码。
- 也知道什么时候应该阻止它继续写。

以及最重要的一点：

**还愿意去做东西。**

可能以后我们真的不会再一行一行地写代码了。甚至“程序员”这个职业本身都会发生非常大的变化。但是只要这个世界上还有问题需要解决，只要我们还有东西想创造，那我觉得，我们应该还是会有事情可以做。只是到那个时候，

代码可能已经不是最重要的那部分了。

## 对代码负责

代码正在变得便宜。实现正在变得便宜。生成正在变得便宜。

**但是判断没有。设计没有。验证没有。**

当代码越来越容易生成，我们真正需要学习的，可能已经不只是怎么写代码。而是怎么对代码负责。

> AI can write the code.  
> You still have to own the system.
